## F-001 / 保守性 / `src/mindmap.ts:109`

> **【対応済み 2026-08-10】** 生の NUL をエスケープ表記に置換。grep / ripgrep が効くことを確認。

**症状**: ソース中に生の NUL バイト (0x00) が 1 個埋まっている。
測定キャッシュのキー連結子として、エスケープ表記ではなくリテラルの
NUL 文字が書かれている(`const key = font + "<NUL>" + text;`、
絶対オフセット 4037、line 109 col 31)。

**再現条件**: `grep` / `ripgrep` で `src/mindmap.ts` を検索する。
または `git diff` / GitHub 上で差分を見る。

**確度**: 確定。`node -e 'fs.readFileSync("src/mindmap.ts").indexOf(0)'` = 4037 を実測。

**影響**:
- ripgrep / grep がこのファイルを **バイナリと判定し、検索から除外する**。
  本監査中も `Grep` ツールが `binary file matches` を返し、`mindmap.ts` 内の
  シンボル検索が全滅した。1814 行 = 最大のファイルがコード検索から見えない
  状態は、以降の保守で一貫して事故要因になる。
- Git が binary 扱いすると差分レビューができない
  (`.gitattributes` なし、リポジトリは未 init)。

**修正方針**: リテラル NUL をエスケープ表記に置き換える。バイト列だけが
変わり意味は等価。区切り文字である必然性もないので通常文字でもよい。

## F-002 / 性能 / `src/main.ts:197` (`applySnap`) → `src/mindmap.ts` `render()`

> **【対応済み 2026-08-10】** `render()` を差分更新化 + 同値 setAttribute の抑止。applySnap+render が 5000 ノードで 134.7ms → 15.9ms（8.5倍）。詳細は PERF.md 末尾。

**症状**: スナップショットを適用するたびに、**内容が 1 バイトも変わって
いなくても**マップ全体の SVG を破棄して作り直す。`render()` は
`edgeLayer.replaceChildren()` / `nodeLayer.replaceChildren()` の後に
全ノードぶんの `<g>` `<rect>` `<text>` を新規生成する。`applySnap()` は
`map.render()` を無条件に呼ぶので、何も起きなかったコマンドでも全再構築が走る。

**再現条件**(実測手順):
1. 2001 ノードの文書を開く (`audit/fixtures/wide.md`)
2. undo スタックが空であることを確認
   (`document.getElementById("btn-undo").disabled === true`)
3. マップペインにフォーカスして `u` (vim undo) を連打する

**確度**: 確定。ブラウザ実測:

| 文書 | ノード数 | SVG 要素数 | 空 undo 1 回のコスト |
|---|---|---|---|
| `mmm.md` | 261 | 1,316 | (基準) |
| `wide.md` | 2,001 | 10,016 | **中央値 66ms**(52.5〜87.2ms, n=20) |

`btnUndo.disabled` は計測中ずっと `true` = undo スタックは空、テキストは不変。
それでも毎回 66ms 消える。

**影響**:
- 空 undo でも 66ms のフリーズ(60fps 換算で 4 フレーム落ち)。
- 一般形のほうが重い: **テキスト編集 1 文字ごとに同じ全再構築が走る**。
  `onUserEdits` → `core.replaceText` → `applySnap` → `render()` の経路が、
  タイプのたびに 10,016 個の SVG 要素を捨てて作り直している。文書が育つほど
  1 文字の入力が線形に重くなる。
- 全再構築は DOM ノードの同一性を壊すので、CSS トランジション・フォーカス・
  DOM 同一性に依存する仕組みが今後一切使えない(拡張の詰まり)。

**修正方針**: (1) `applySnap` の入口で「テキストと nodes が前回と同一なら
`render()` をスキップ」の早期リターン(`rev` か テキスト長+ハッシュで判定)。
(2) 本質的には `render()` を差分更新にする — `boxes` の id をキーに既存 `<g>`
を使い回し、`transform` と寸法だけ書き換える。(1) は数行、(2) は `render()`
の作り直し。

## F-003 / バグ / `src/mindmap.ts` (`onKeydown` の `u` 分岐) + `src/main.ts:440`

## F-004 / バグ / `core/cmds.mbt` `cmd_outdent` が出す編集の形

**症状**: outdent(段上げ)で、対象が**その親の最後の子**であるとき、
ノードの **id が捨てられる**。id はユーザーの選択集合の鍵なので、
その場で選択が外れる。

**訂正**: 本監査の初版ではこれを「outdent は必ず id を捨てる」と書いたが、
実測の結果**条件付き**であることが分かった。後続の兄弟がある場合は
ブロックの再配置が必要になり、`move_block` の `at_hs` による id 復元が
働くため id は保たれる。最後の子のときだけ移動が不要で、
「見出し先頭の `#` を 1 個消す」純削除だけが残り、これが破壊扱いされる。

| 状況 | outdent が出す編集 | id |
|---|---|---|
| 後続の兄弟あり | `#` 削除 + ブロック移動 | **保存**(move_block が復元) |
| 後続の兄弟あり + 親に後続あり | 同上 | **保存** |
| 自分に子がある + 兄弟あり | 同上 | **保存** |
| **最後の子** | `#` の純削除のみ | **消失** |
| **最後の子 + 親に後続あり** | 同上 | **消失** |
| **最後の子 + 自分に子がある** | 同上 | **消失** |

**根本原因**: `core/doc.mbt` の `map_offset` は、見出し開始オフセットちょうどの
編集について次のように場合分けしている。

| 編集の形 | 扱い |
|---|---|
| 置換(`to > from` かつ insert が非空) | 行の書き換え → **位置は生存** |
| 純削除(`to > from` かつ insert が空) | **無条件に破壊 → -1** |
| 純挿入で改行終わり | 上に行ができる → 位置はずれるが生存 |
| 純挿入で改行終わりでない | 行の書き換え → 生存 |

網羅マトリクス(`audit/identity-matrix.md`、19 通りを実測)では
**id を失うのはこの「見出し先頭ちょうどの純削除」2 通りだけ**である。

**再現条件**(実機で確認):
1. `# root / ## a / ### a1 / #### a11` を開く
2. 地図で `a1` と `a11` を複数選択(`Ctrl+クリック`)
3. `Shift+Tab`(段上げ)を押す

**確度**: 確定。
- 単体: `audit/tests/commands.test.mjs` の C9b が失敗、C9a(indent)は成功。
- 実機: 選択が `["a1","a11"]` → **`[]`(空)**。indent(`Tab`)では保たれる。
- 条件の切り分け: 6 パターンを直接実行して上表を得た。

**影響**:
- 段上げのたびに選択が外れるので、**2 段階の段上げを連続でできない**。
- `applySnap` が生存ノードで選択を間引く設計(`src/main.ts:184` 付近)なので、
  id が消える = ユーザーの選択が消える、が直結している。
- 将来 id にひもづく状態(折り畳み・ノート・装飾)を足すと、
  段上げのたびに黙って失われる。

**修正方針(実測で検証済み・コアの変更不要)**:
`cmd_outdent` が `#` を消すとき、**削除ではなく置換として出す**。
つまり `Edit{from: hs, to: hs+1, insert: ""}` の代わりに
`Edit{from: hs, to: hs+2, insert: "#"}`(ハッシュ列を 1 つ短いものへ置換)。

実測: 同じ文書に対して両者が**バイト単位で同一のテキスト**を生成し
(`"# r

## p

## target
"`)、置換形では **id が保存される**。
`map_offset` は「見出し先頭の置換 = 行の書き換え = 生存」を既に持っているので、
コア側の同一性機構には一切手を入れずに済む。

## F-005 / バグ / `core/doc.mbt` `rebuild_nodes`(重複ルートの破棄)+ 部分木範囲

> **【対応済み 2026-08-10】** ノードの範囲 `[hs, sub_end)` を、「ノードにならないが飛ばしてはいけない境界」で打ち切るようにした (`core/doc.mbt` の `rebuild_nodes`)。境界は (a) 構造から外した 2 つ目以降の `#`(常に境界)と (b) `<!--` / `-->` のマーカー(**対を割るときだけ**境界。領域がまるごと部分木の内側にあるなら切らない — 子を折り畳んだだけで親から切り離されるため)。あわせて `recompute_parents` が「範囲が既に閉じた祖先は親にしない」ようになり、子の範囲が親の範囲に必ず含まれる。回帰テスト 4 件を追加(コア 52/52 pass)。監査の往復テストは 22→24 pass。

**症状**: 2 つ目以降の `#` 見出しは**構造からは外される**が、テキストからは
消えないし、**直前のノードの部分木範囲 (`subEnd`) からも除外されない**。
その結果、地図に見えていないテキストが、隣のノードの一部として
削除・コピー・移動・hide に巻き込まれる。

README は「2 つ目以降の `#` は構造として無視される(**行は保存される**)」と
明記しているが、保存されない。

**再現条件**:
```md
# root

## a

本文A

# 二つ目のルート

## b

本文B
```
1. 地図でノード `a` だけを選択する(`# 二つ目のルート` は地図に存在しない)
2. `Delete` を押す

**確度**: 確定。実測:

| 操作 | 結果 |
|---|---|
| パース | `a` の `subEnd` が `# 二つ目のルート` 行を飲み込む(部分木 = `"## a\n\n本文A\n\n# 二つ目のルート\n\n"`) |
| `delete(a)` | 残り = `"# root\n\n## b\n\n本文B\n"` — **`# 二つ目のルート` が消滅**(40文字中22文字が消える) |
| `copy(a)` | クリップボード = `"## a\n\n本文A\n\n# 二つ目のルート\n"` — 貼ると余計な `#` が増殖 |
| `hide(a)` | `# 二つ目のルート` ごとコメントアウトされる |

**影響**:
- **無選択のテキストが黙って消えるデータ欠損**。地図側には
  `# 二つ目のルート` を表す要素が無いので、ユーザーには失われたことが
  分からない。undo でしか戻せず、保存後に気づけば復旧手段が無い。
- `#` を2つ以上書くのは通常の Markdown として普通(章立てされた文書、
  複数の記事を1ファイルにまとめたメモなど)。特殊入力ではない。
- コピー経路では逆に `#` が**増える**ので、貼り付けを繰り返すと
  ルート候補が増殖していく。

**修正方針**: 構造から外した `#` 見出しを、部分木範囲の計算では
「深さ1の境界」として扱う(ノードにはしないが `sub_end` は打ち切る)。
`rebuild_nodes` で捨てている重複ルートの `hs` を境界リストとして残し、
`sub_end` 解決時に参照すればよい。
併せて「地図に出ないテキストがノードに含まれている」ことを
UI で可視化するか、そもそも 2 つ目の `#` を別ツリーとして描くかは要設計判断。

## F-006 / バグ / `core/cmds.mbt` `cmd_move` (ルート兄弟への移動)

**症状**: ノードをルートの**兄弟**位置(`pos=1`/`2`)へ移動すると、
そのノードが深さ1に昇格して `#` が2つになる。単一ルート規約により
先頭の `#` だけが構造に残るので、**元のルートが地図から丸ごと消える**
(子は新しいルートに付け替えられる)。

**再現条件**(コア API 直叩き):
```js
initDoc("# root\n\n## a\n\n### a1\n\n## b\n");
moveNodes([bのid], rootのid, 1);   // または 2
```
→ ノード数 4 → 3、`root` の id が構造から消える。

**確度**: 確定(`audit/tests/commands.test.mjs` C10b が失敗)。
ただし**現状の UI からは到達しない**: `src/mindmap.ts:1641` の
`updateDrop` が深さ1へのドロップを問答無用で `pos=0`(子)に倒している。

**影響**:
- 今は潜在。ただし不変条件が **UI 側の 1 行のガードだけ**で守られており、
  コア API 自体は無防備。キーボードからの移動、コマンドパレット、
  別のドロップ経路、API の再利用が増えた時点で即座に顕在化する。
- `cmd_add_root` には「2つ目のルートを作らない」ガードがあるのに、
  `cmd_move` には無い。同じ不変条件が 1 箇所でしか守られていない。

**修正方針**: `cmd_move` の入口で「移動先が深さ1 かつ pos が兄弟」を
拒否する(`cmd_add_root` と同じ位置に同じ不変条件を置く)。
F-005 を直すなら、そちらと同じ「重複ルート」ロジックの一部として扱う。

## F-007 / バグ / `core/cmds.mbt` `cmd_toggle_hidden`(閉じマーカーの挿入)

**症状**: 末尾に改行が無い文書で hide → show すると、**末尾に改行が1つ増える**。
hide は閉じマーカーを `"\n-->\n"` として挿入する(直前が改行でないときだけ
`\n` を前置)が、show は `-->` の**行だけ**を削除するため、前置した `\n` が
残る。往復が非可逆。

**再現条件**:
```js
initDoc("# r\n\n## a");     // 末尾改行なし
toggleHidden(aのid);         // -> "# r\n\n<!--\n## a\n-->\n"
toggleHidden(aのid);         // -> "# r\n\n## a\n"   ← 元と違う
```

**確度**: 確定(`audit/tests/commands.test.mjs` C6 が失敗)。
なお `core/core_test.mbt` の `"hide at EOF without trailing newline"` は
**この挙動をそのまま期待値として固定している**ので、既存テストは
これを欠陥として検出しない。

**影響**:
- 軽微だが、ユーザーが編集していない箇所に差分が出る。
  末尾改行を持たない運用(一部の設定ファイル、他ツール生成の md)では
  hide/show を触るたびに git 差分が汚れる。
- undo は編集列の逆適用なので正しく戻る。壊れるのは show 経路だけ。

**修正方針**: hide 時に前置した `\n` を、閉じマーカーの削除範囲に含める
(挿入した範囲をそのまま記録して show で使う)。または hide 側で
`\n` を前置せず、末尾改行が無い場合は本文末に改行を足さない形にする。

## S-002 / XSS: エクスポートした SVG を文書として開いても実行されない / 確定

**やったこと**: 上記のスクリプト入り SVG を含む文書でマップを SVG
エクスポートし、その出力を `Blob` → `blob:` URL にして **iframe に
文書として読み込ませ**、スクリプトが動くかを観測した。

- エクスポート結果に**ペイロードは確かに埋め込まれている**
  (data URL 内に URL エンコードされた `%3Cscript%3E` と `onload=` を確認。
  デコードして中身も確認済み)。したがってこの検査は空振りではない。
- それでも `window.__XSS_EXPORT` / `__XSS_SVG` / `__XSS_ONLOAD` は
  **全て未定義のまま**。`<image>` の中の SVG は画像として扱われ、
  スクリプトは動かない。

**結論**: 「信頼できない .md を開く」「そのマップを SVG に書き出して配る」の
どちらの経路でもスクリプト実行は起きない。

**ただし残る注意点(実行はされないが情報として)**:
エクスポート SVG には**元文書のテキストがそのまま埋め込まれる**
(hidden ノードのラベルも含む。`exportSvg` は `selected` などの一時 class を
外すだけで、hidden ノードは除外しない)。コメントアウトして隠したつもりの
内容が、書き出した SVG には見える形で残る。

## F-008 / 性能・バグ / `src/mindmap.ts:1274` (node-editor の input ハンドラ)

> **【対応済み 2026-08-10】** `input` に composition ガードを追加。変換確定まで rename せず、compositionend で 1 回だけ反映する。

**症状**: ラベル編集欄の `input` ハンドラに **composition ガードが無い**ため、
IME 変換中の**中間候補が 1 つ残らず markdown 文書に書き込まれ**、そのたびに
`rename` → `applySnap` → `render()`(全再構築)が走る。

```ts
this.editor.addEventListener("input", () => {
  if (this.editingId !== -1) {
    this.host.rename(this.editingId, this.editor.value, this.editingTag);
    this.positionEditor();
  }
});
```

同じファイルの `keydown` ハンドラ(`src/mindmap.ts:1280`)には
`if (e.isComposing || e.keyCode === 229) return;` があり、マップペインの
`onKeydown` と `src/main.ts` の window リスナにも同じガードがある。
**`input` だけがガードされていない。**

**再現条件**: マップでノードを選び `i` で編集開始 → 日本語を IME で入力する。
変換を確定する前から、左の md ペインに未確定の候補文字列が次々に反映される。

**確度**: 確定。実測(261 ノードの `mmm.md`):

| 変換候補 | 文書に書かれたか | その 1 回のコスト |
|---|---|---|
| `k` | ✔ | 7.1ms |
| `か` | ✔ | 9.6ms |
| `かん` | ✔ | 11.1ms |
| `かんじ` | ✔ | 12.4ms |
| `漢字` | ✔ | 12.9ms |

**影響**:
- 未確定の候補が文書に入るので、md ペインが変換中ずっとちらつく。
- コストが F-002 と積算される。候補 1 つごとに全再構築なので、
  **5,000 ノードの文書では 1 候補 70ms**(PERF.md 2 節のモデルより)。
  5 候補の語を 1 つ変換するだけで 350ms 固まる。日本語入力が実用にならない。
- 変換を中断(Esc)した場合でも、中間候補が書かれた状態が一度は
  文書とスナップショットを通過している。

**なお undo の粒度は正しい**: 実測で **1 回の undo で編集開始前に戻る**
(`editingTag` が編集セッション全体で 1 つなので、コア側でタグ合体される)。
つまり問題は undo ではなく、書き込み頻度と再描画コストにある。

**修正方針**: `input` ハンドラの先頭で
`if ((event as InputEvent).isComposing) return;` として変換確定まで
`rename` を遅らせ、`compositionend` で 1 回だけ確定させる
(`src/editor.ts` が md ペイン側で既に採っている方式と揃う)。
表示だけライブに見せたいなら、`positionEditor()` の呼び出しだけ残せばよい。

## F-009 / バグ / `src/main.ts` (persistNow / boot 復元、`storage` イベント未購読)

**症状**: 同じアプリを**2つのタブで開くと、互いの編集を黙って上書きする**。
両タブが 250ms デバウンスで `localStorage["mmm.text"]` に文書全体を書き込むが、
どちらも `window.addEventListener("storage", ...)` を購読していないため、
相手の変更に気づかない。最後に書いたタブの内容だけが残る。

**再現条件**(実機で実行済み):
1. タブ A でアプリを開き、ノードを1つ追加する(ラベル「タブAが作ったノード」)
2. 300ms 待つ → `localStorage` に A の編集が入ることを確認
3. **別タブ B** で同じ URL を開く
4. B でノードを1つ追加する(ラベル「タブBが作ったノード」)
5. 300ms 待って `localStorage` を見る

**確度**: 確定。実測結果:

| 観測点 | 結果 |
|---|---|
| B を開いた時点で B が見ているノード数 | 261(A の 262 ではない) |
| B の画面に A の編集が反映されたか | **いいえ** |
| B の編集後、localStorage に A の編集が残っているか | **いいえ(消えた)** |
| B の編集後、localStorage に B の編集があるか | はい |

**影響**:
- タブ A の作業が、A では画面上に見えているのに**永続層からは消えている**。
  A をリロード/再起動した瞬間に A の編集が失われる。
- 「エディタを2つ開いて見比べる」は普通の使い方であり、特殊操作ではない。
- ファイル名 (`mmm.fileName`) も同様に上書きされる。
  ただし IndexedDB のファイルハンドルについては起動時に
  `if (h && h.name === fileName) fileHandle = h;` の突き合わせがあるため、
  別ファイルのハンドルを掴む事故は防がれている(このガードは正しく機能する)。
- `beforeunload` はメモリ上のテキストと `savedText` を比べるので、
  A を閉じるときには警告が出る。だが警告は「未保存の変更がある」であって
  「別タブに上書きされた」ではないので、原因が分からない。

**修正方針**: 最小対応として `window.addEventListener("storage", ...)` で
`mmm.text` の外部変更を検知し、ダーティでなければ再読込、ダーティなら
ヘッダーに衝突を表示する(`flashFilename` の仕組みが使える)。
本格対応は BroadcastChannel か Web Locks で単一書き手を決めること。

## F-010 / バグ / `src/main.ts` の CodeMirror ⇄ コア のオフセット境界

> **【対応済み 2026-08-10】** アプリ内は常に LF に統一した。読み込み 3 経路（openFile / 非FS の file input / ドラッグ&ドロップ）で `adoptText()` が `\r\n` と単独 `\r` を LF へ潰し、元の改行種別を `mmm.eol` に永続化する。保存時だけ `toFileEol()` で書き戻す。起動時の localStorage 復元も正規化し、`mmm.eol` が無い旧データは 本文から判定して移行する。実機確認: CRLF 文書で `## gamma` 行末に `Z` を打鍵 → コアの本文が `## gammaZ`（正しい位置）、マップのノードも失われない。

**症状**: **CRLF 改行の .md を開いて md ペインで 1 文字打つと、その文字が
6 文字ずれた位置に書き込まれ、文書が静かに壊れる。** 2 つのペインが
別々の内容を持った状態になり、画面に見えているのは正しいのに、
保存されるのは壊れた方である。

原因: CodeMirror 6 は読み込んだ文書の改行を内部で LF に正規化する
(`lineSeparator` 未指定のため)。一方コアは受け取った生テキストを
そのまま保持する(CRLF のまま)。`onUserEdits` は CodeMirror が出した
**LF 基準のオフセット**をそのままコアの `replaceText` に渡すので、
その位置より前にある改行の数だけ位置がずれる。

**再現条件**(実機で実行済み):
1. CRLF の文書を開く: `# root\r\n\r\n## alpha\r\n\r\n## beta\r\n\r\n## gamma\r\n`
2. md ペインで `## gamma` 行の末尾にキャレットを置く
3. `Z` を 1 文字打つ

**確度**: 確定。ブラウザ実測:

| 観測点 | 値 |
|---|---|
| md ペインの表示 | `## gammaZ`(正しい) |
| コアの実テキスト | `...## beta\r\n\r\n##Z gamma\r\n` — **`Z` が 6 文字手前に入った** |
| `Z` が入った位置 | 35(コア側で正しい位置は 41) |
| マップのノード | `[root, alpha, beta, gamma]` → **`[root, alpha, beta]`**(gamma が消滅) |

ずれ幅は「その位置より前にある改行の数」なので、**文書の下へ行くほど
大きくずれる**。長い文書では見当違いの場所が書き換わる。

**影響**:
- **Windows で作られた .md はほぼ CRLF** なので、対象は例外的な入力ではない。
- 見えているもの(CodeMirror)と保存されるもの(コア)が食い違うため、
  ユーザーは壊れたことに気づけない。そのまま `Mod+S` すると
  **壊れたテキストがディスクに書かれる**。
- 見出し行が壊れるとノードが構造から消えるので、マップからも失われる。
- マップ側の選択ハイライト(`editor.highlight`)も同じオフセットを使うので
  常時ずれる。

**なぜ既存のテストで見つからなかったか**: コア単体の往復テストは CRLF を
通しており(`audit/tests/roundtrip.test.mjs` の P1「CRLF 混在」)、**コアは
正しい**。壊れているのは UI とコアの継ぎ目であり、そこを検査するものが
1 つも存在しない(`audit/MAP.md` 6.3 が指摘している「両ペインの収束を
検証する仕組みがテストにもランタイムにも無い」がそのまま顕在化した形)。

**修正方針**: 読み込み時に改行を正規化して**片方に寄せる**のが最も安い。
`openFile` / drop / localStorage 復元のすべてで `text.replace(/\r\n/g, "\n")`
してからコアと CodeMirror の双方に渡し、保存時に元の改行へ戻す
(元が CRLF だったかを 1 フラグ持つ)。
コア側は既に `nl()` で文書の改行種別を見ているので、
**コアを LF 前提にしても振る舞いは変わらない**。
根治するなら CodeMirror に `EditorState.lineSeparator` を設定して
正規化させない方向もあるが、CRLF のままだと CodeMirror 側の
行操作コマンドが素直に動かないので、LF に寄せる方が安全。

**併せて**: 両ペインの収束を検証するランタイムアサート
(開発ビルドで `editor.text() === core.getText()` を編集ごとに確認)を
入れておけば、この種の継ぎ目バグは即座に露見する。

## F-011 / バグ / `core/parser.mbt` `is_marker_line`(閉じマーカーの厳密一致)+ 無通知

**症状**: `<!--` で開いた hide 領域の閉じマーカーが 1 文字でも違うと、
領域が**文書の最後まで閉じない**。その間のノードは全部 hidden 扱いになるが、
**UI にはどこにも「閉じていない」という表示が無い**。

**これは仮想の話ではなく、リポジトリ同梱の `mmm.md` で現に起きている**
(監査中に、ユーザーがこのファイルを編集した結果として観測):

| 観測 | 値 |
|---|---|
| 335 行目 | `<!--` — 有効な開始マーカー |
| 528 行目 | `--->` — **ハイフンが 1 つ多く、閉じマーカーとして認識されない** |
| 結果 | 273 ノード中 **108 ノードが hidden**(「そのに」以降、末尾まで全部) |

そしてユーザー自身が同じファイルの中に
「**コメントアウトの挙動 / 閉じてるはずなのにそのあともなる**」と
書いている。**観測されている症状の原因がこれ**である。

**再現条件**:
1. 任意のノードで `H` を押して hide する(`<!--` と `-->` が入る)
2. md ペインで閉じ側を `--->` や `-- >`、`- ->` のように 1 文字変える
   (あるいは最初から手で `<!--` だけ書く)
3. それ以降の全ノードが薄い hidden 表示になる

**確度**: 確定。`core/parser.mbt` の `is_marker_line` は行をトリムした結果が
`"-->"` と**完全一致**することを要求する。`scan_doc` は閉じられなかった領域を
`(open, next, -1, -1)` として返し、`rebuild_nodes` はそれ以降の見出しすべてに
`hidden: true` を立てる。実測で `mmm.md` の hidden ノード数 108 を確認した。

**影響**:
- 文書の大半が「無効化」状態になるのに、原因を示すものが何も無い。
  マップが薄くなるだけなので、ユーザーは「バグった」としか分からない
  (実際にそう報告されている)。
- md としても本当に HTML コメントなので、**GitHub 等の外部レンダラでは
  そこから先が丸ごと消える**。保存して共有すると内容が失われて見える。
- 閉じマーカーは手で書き換えられる位置にあり、タイプミス 1 文字で起きる。

**修正方針**(いずれも小さい):
1. **可視化**: 閉じられていない領域があるとき、ヘッダーか該当ノードに
   警告を出す(`flashFilename` の仕組みが既にある)。
   `scan_doc` は `close == -1` で未閉鎖を既に検出しているので、
   スナップショットにフラグを 1 つ足せば UI 側で出せる。
2. **許容**: `-->` の判定を「`-` が 2 個以上 + `>`」程度に緩める
   (`is_separator` が既に同様の緩い判定をしている)。
3. **UI から解除できるようにする**: 現状 hidden の解除は `H` だけで、
   マーカーが壊れていると対象ノードを選べないことがある。
   ユーザーの その３ の要望「ui, keyboard から指定、解除できるように」と同じ。

**注記**: この所見は監査対象の `mmm.md` がユーザーによって編集された結果として
観測された。監査自体は `mmm.md` に一切書き込んでいない。
