# ノード同一性の実測マトリクス

フェーズ2の「ノードの同一性は何で担保されているか。それが崩れる操作はどれか」
という問いに対する**実測による網羅回答**。
(この観点の探索エージェントはセッション上限で落ちたため、ここで直接測った)

## 前提

- 同一性の代理キーは **見出し行の開始文字オフセット**。
  `core/doc.mbt` の `map_offset` が編集前オフセットを編集後へ写し、
  `rebuild_nodes` が `id_at` マップで id を再利用する。
- 検査文書: `"# root\n\n## parent\n\n### target\n\n本文\n\n### sibling\n"`
- 対象ノード: `### target`(深さ3)(id 3)
- 「保存」= 編集後のノード列に**同じ id が残っている**こと。

## 読み取れる規則

- 保存されるのは 18 通り、消失するのは 1 通り。
- **消失する組合せ**:
  - 純削除 / 対象の見出し先頭ちょうど(行全体)(見出しごと消す)

## 結論

`map_offset` は「**改行で終わらない純挿入 = その行の書き換え = 位置は生存**」
という規則を持つ。これは indent(`#` を 1 個足す)を救うために入れられた規則である。

ところが**対になる純削除には同じ規則が無く、見出し開始位置ちょうどでの削除は
無条件に「見出しが壊れた」と扱われる**。**同じ操作の逆向きが非対称**である。

これが F-004 の直接原因。ただし **outdent が常に id を失うわけではない**:
後続の兄弟があるときはブロックの再配置が走り、move_block の at_hs による
id 復元が働くため保たれる。id を失うのは **「対象が親の最後の子」**
= 移動が不要で純削除だけが残るとき(6 パターンを直接実行して確認)。

**帰結として、修正は極めて安い**: 上表のとおり「見出し先頭ちょうどの**置換**」は
深さを増やしても減らしても id を保存する。つまり outdent がハッシュを
「削除」ではなく「ハッシュ列の置換」として出せば、テキストはバイト単位で
同一のまま id が保たれる(実測で確認)。map_offset には手を入れなくてよい。ただし **outdent が常に id を失うわけではない**:

## id が変わると何が壊れるか

id に依存している上位の仕組み(すべて `src/` 側):

| 仕組み | 場所 | id が変わったときの挙動 |
|---|---|---|
| 選択集合 `selection` | `src/main.ts:32` | `applySnap` が生存ノードで間引くので**選択から外れる** |
| アンカー `anchorId` | `src/main.ts:33` | 消えると選択の最後の要素か -1 に落ちる |
| `byId` マップ | `src/main.ts:31` | 再構築されるので古い id は解決不能 |
| SVG の `g.dataset.id` | `src/mindmap.ts:595` | 再描画で新 id に置き換わる |
| `boxes` / `order` | `src/mindmap.ts:183-184` | 同上 |
| ドラッグ中の `dragging.subtree` | `src/mindmap.ts` | ドラッグ中に id が変わると対象を見失う |
| 編集中の `editingId` | `src/mindmap.ts:185` | 編集中に id が変われば以後の `rename` が無効になる |

つまり **id の寿命 = ユーザーの選択・編集セッションの寿命**であり、
id を捨てる編集はそのまま UI 状態を捨てる編集になる。
