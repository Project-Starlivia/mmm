(`test/fixtures/`)。同じ入力でしか比較しないため、乱数はシード固定。

### 計測できなかったもの / 使えなかった経路

1. **Claude_Browser のペイン経由ではフレーム計測が成立しない。**
   実測: `document.hidden === true`、`visibilityState === "hidden"`、
   `requestAnimationFrame` が **2.5 秒で 0 回**しか発火せず、
   `performance.getEntriesByType("paint")` も空。
   → パン/ズーム/描画のフレーム時間はこの経路では測れない。
   本ファイルの数字はすべて Playwright 側のもの。

2. **detached DOM ノード数は未計測。**
   `Memory.getDOMCounters` が空を返した(Memory ドメイン未有効化)。
   正確に出すには `HeapProfiler.takeHeapSnapshot` を取って
   detached ノードを数える必要がある。
   **必要なセットアップ**: CDP で `HeapProfiler.enable` →
   `takeHeapSnapshot` → スナップショットを解析(数十 MB の JSON を
   パースする処理が別途必要)。今回は代わりに、生きている DOM ノード総数の
   推移で代替した(下記 4 節)。

3. **`performance.memory` はヒープ判定に使えない。**
   Chromium が量子化しており、400 回編集の前後で 0.1MB 単位まで完全に
   同値になった。ヒープは CDP の
   `HeapProfiler.collectGarbage` → `Runtime.getHeapUsage` で測り直した。

4. **「5分編集後」は実時間 5 分ではなく編集 400 回で代替した。**
   実時間で回すと dev サーバの HMR やブラウザのバックグラウンド化が
   混ざるため。回数と手順は 4 節に明記する。

5. **production build 未計測。** dev サーバは ES モジュールを個別配信するため、
   初回表示のうちモジュール読み込みぶんは本番より不利に出る。
   ただし本ファイルの主要な結論(入力遅延)は初回表示とは独立。

## 2. 一番大きい発見: 入力遅延は SVG 要素数に比例する

6 fixture の実測に直線を当てはめると、当てはまりが極めて良い:

```
1文字入力の反映遅延(p50) ≒ 1.11ms + 0.00263ms × (SVG 要素数)
```

| fixture | SVG 要素数 | 実測 p50 | モデル予測 | 差 |
|---|---|---|---|---|
| `fat` | 26 | 1.2ms | 1.2ms | 0.0 |
| `deep` | 1,011 | 4.0ms | 3.8ms | −0.2 |
| `baseline` | 1,316 | 4.6ms | 4.6ms | 0.0 |
| `rich` | 3,616 | 11.5ms | 10.6ms | −0.9 |
| `wide` | 10,016 | 25.8ms | 27.5ms | +1.7 |
| `mixed` | 26,051 | 70.2ms | 69.7ms | −0.5 |

**支配変数はノード数ではなく SVG 要素数である。** これは `rich` が証明している:
`rich` はノード数 301 で `baseline`(261)とほぼ同じなのに、入力遅延は
4.6ms → 11.5ms と 2.5 倍になる。違いは 1 ノードあたりの SVG 要素数:

| fixture | ノード | SVG 要素 | **要素/ノード** |
|---|---|---|---|
| `baseline` | 261 | 1,316 | 5.04 |
| `wide` | 2,001 | 10,016 | 5.01 |
| `mixed` | 5,000 | 26,051 | 5.21 |
| `rich` | 301 | 3,616 | **12.01** |

`rich` はコードブロックのプレビュー行(`code-bg` の矩形 + 最大 6 行の
`code-line` テキスト)を持つため、1 ノードが 12 要素に膨らむ。
コンテンツカードを 1 種類足すたびに、**全文書の入力遅延が要素数に比例して悪化する**。

### 実用上の意味

60fps を守れる予算を 16ms とすると、モデルから逆算して
**SVG 要素 約 5,700 個** が上限。要素/ノード = 5 なら約 1,100 ノード、
コードブロックを多用して 12 なら約 470 ノードで 1 フレーム分を使い切る。
`mixed`(5,000 ノード)では 1 打鍵ごとに 70ms、つまり **4 フレーム落ちる**。

## 3. 遅い上位 3 件の内訳

「遅い」の実体は全て同じ 1 本の経路である:
`onUserEdits` → `core.replaceText` → `applySnap`(`src/main.ts:197`)→
`map.render()`。`render()` は `edgeLayer.replaceChildren()` /
`nodeLayer.replaceChildren()` で全消去してから全ノードを作り直す。

### 3-1. 経路の切り分け(`docs/audit/perf-detail.json`)

同じキー入力でも、**描画を通る経路と通らない経路**でコストが 2 桁違う:

| fixture | 何も変化しない undo(applySnap + render を通る) | 選択移動 `j`(render を通らない) | 比 |
|---|---|---|---|
| `baseline` | p50 **6.7ms** / p95 8.7ms | p50 0.3ms | 22× |
| `rich` | p50 **21.4ms** / p95 29.4ms | p50 1.6ms | 13× |
| `wide` | p50 **53.3ms** / p95 72.7ms | p50 0.7ms | 76× |
| `mixed` | p50 **134.7ms** / p95 160.1ms | p50 1.4ms | 96× |

undo スタックは空(`btn-undo` は `disabled`)、テキストは 1 バイトも変わって
いない。それでも `mixed` では 1 回 134.7ms かかる。
→ コストは「変更を反映すること」ではなく「無条件に作り直すこと」にある
(F-002 / F-003)。

### 3-2. CPU プロファイルの内訳(15 打鍵ぶんの self time)

CDP `Profiler`(サンプリング間隔 100µs)。数字は 15 回の打鍵を含む
計測窓全体の self time 合計。

| 関数 | `baseline` | `rich` | `wide` | `mixed` |
|---|---|---|---|---|
| `(program)`(V8 が JS フレームに帰属できない = ブラウザ内部の DOM/style/layout) | 158ms | 398ms | 976ms | **2,020ms** |
| `setAttribute` | 10.2 | 33.7 | 69.3 | **197.1** |
| `replaceChildren` | 8.3 | 24.6 | 56.0 | **154.5** |
| `render` (`src/mindmap.ts:178`) | 8.1 | 22.1 | 52.2 | **128.8** |
| `(garbage collector)` | 3.2 | 19.2 | 52.8 | **108.2** |
| `createElementNS` | 3.8 | 16.1 | 40.3 | **107.8** |
| `append` | 6.4 | 12.4 | 34.2 | **94.9** |
| `svgEl` (`src/mindmap.ts:64`) | 3.8 | 13.9 | 29.1 | **82.8** |
| `measure` (`src/mindmap.ts:23`) | — | 14.7 | 24.9 | **75.7** |
| `snap` = `JSON.parse` (`src/coreApi.ts:2`) | — | — | — | **28.4** |

読み取れること:

- **時間の大半は JS ではなくブラウザ内部** (`(program)`)。これは
  26,051 個の SVG 要素を毎回破棄・生成することによる style 再計算と
  レイアウトである。JS 側の最適化では減らない。**要素を作り直さないこと**
  でしか減らない。
- 純粋な DOM 構築 API(`setAttribute` + `createElementNS` + `append` +
  `replaceChildren` + `svgEl`)だけで `mixed` は **637ms**。
- GC が 108ms。使い捨ての SVG 要素を毎回大量に生成しているコスト。
- `measure`(canvas `measureText`、`src/mindmap.ts:23`)はキャッシュ付きなのに
  `mixed` で 75.7ms。キャッシュキーの生成と Map 探索が 26,000 回走るため。
- `JSON.parse`(`src/coreApi.ts:36` の `snap`)が 28.4ms。
  コアとの境界が「全ノード配列を毎回 JSON 化して毎回パースする」設計
  であることの直接コスト。文書が大きいほど比例して増える。

**注意**: `(program)` は計測窓全体(打鍵間の 20ms 待ちを含む)の値なので、
「1 打鍵あたり」に割ってはいけない。1 打鍵あたりの実測値は 2 節の
入力遅延(`mixed` で p50 70.2ms)を見ること。この表は**内訳の比率**を示す。

## 4. パン・ズーム・Hide/Show は速い(ボトルネックではない)

全 fixture で **フレーム時間 p95 = 16.7〜16.8ms、50ms 超えのフレームは 0 本**。

**この「速い」は測り漏れではないことを確認済み**: パン前後・ズーム前後で
`#map-svg > g` の `transform` 属性が実際に変化していることを検証した
(`docs/audit/perf-detail.json` の `panActuallyMoved` / `zoomActuallyChanged` が
全 fixture で `true`)。

| fixture | パン>16ms | パン>50ms | ズーム>16ms | ズーム>50ms | Hide/Show>16ms | Hide/Show>50ms |
|---|---|---|---|---|---|---|
| `baseline` | 4 | 0 | 0 | 0 | 3 | 0 |
| `rich` | 4 | 0 | 5 | 0 | 4 | 0 |
| `deep` | 3 | 0 | 5 | 0 | 1 | 0 |
| `wide` | 2 | 0 | 5 | 0 | 4 | 0 |
| `mixed` | 6 | 0 | 4 | 0 | 2 | 0 |

理由は構造から明確: パンとズームは `viewport` の `transform` 属性 1 つを
書き換えるだけで `render()` を通らない。**このアプリで唯一、DOM を作り直さない
経路であり、唯一 60fps を保てている経路でもある。**

なお「展開・折りたたみ」に相当する機能はこのアプリに存在しない
(折り畳みは実装しない方針)。相当する操作として `H`(Hide/Show)を計測した。

## 5. ヒープと DOM ノード数

`mixed`(5,000 ノード)で、md ペインに 400 文字を打ち(25 打鍵ごとに undo を 1 回
挟む)、その後マップのホイールズーム 60 回を追加。
各サンプルの前に CDP `HeapProfiler.collectGarbage` を実行している。

| 時点 | ヒープ使用 | ヒープ総量 | DOM ノード総数 | SVG 要素数 | マップノード数 |
|---|---|---|---|---|---|
| 編集前 | 13.20MB | 14.37MB | 26,265 | 26,051 | 5,000 |
| 400 回編集後 | 14.99MB | 17.99MB | 26,316 | 26,051 | 5,000 |
| マップ操作も追加後 | 15.01MB | 15.74MB | 26,316 | 26,051 | 5,000 |

- ヒープ増分 **+1.81MB**(GC 後の値どうしの比較)。
- **DOM ノード数は増えない**(26,265 → 26,316、+51 は CodeMirror の行要素)。
  つまり `render()` が毎回全消去することによる**生きている DOM の膨張は無い**。
- 400 回の編集で 1.81MB 増えたが、暴走的な増加ではない。
  ただし **detached ノードの蓄積は今回計測していない**(0 節参照)。
  DOM ノード総数が一定なので、少なくとも「捨てた要素が生きたツリーに
  残り続ける」形のリークは無い。

編集 400 回にかかった実時間は **79.8 秒 = 1 回あたり 199.5ms**
(Playwright のキー送出オーバーヘッドと 16 回の undo を含む参考値。
純粋な入力遅延は 2 節の p50 70.2ms のほう)。
**5,000 ノードの文書では「400 文字打つのに 80 秒」がこのアプリの現状**という
体感値になる。

## 7. 計測から言えること(数字の範囲内で)

1. 唯一のボトルネックは `applySnap` → `render()` の全再構築であり、
   コストは SVG 要素数に線形(1.11ms + 0.00263ms/要素)。
2. `render()` を通らない操作(パン・ズーム・選択移動)は全サイズで速い
   (60fps 維持、選択移動は 1.6ms 以下)。したがって遅さは
   「マップが大きいこと」ではなく「毎回作り直すこと」に起因する。
3. コンテンツカード(コードブロック等)は 1 ノードあたりの要素数を
   5 → 12 に増やし、入力遅延を同じ比率で悪化させる。
   種類を増やすほど全文書が遅くなる。
4. コアのパースは全体再解析でも 19.1ms で、律速ではない。
5. 生きている DOM は膨張しない。ヒープは 400 編集で +1.81MB。

# 追記: 差分レンダリング後の再計測（2026-08-10）

監査の指摘 F-002 を受けて `render()` を差分更新に作り替えたので、
**同じハーネス・同じ probe** で測り直した。

## 比較できる指標: applySnap + render の実コスト

「何も変わらない undo」を叩いたときの所要時間(p50)。テキストは 1 バイトも
変わらないので、純粋に「スナップショットを適用して描画する」コストだけが出る。
`test/tools/perf-detail.ts` の probe は変更していないので直接比較できる。

| 文書 | ノード | 改修前 | 差分レンダのみ | + 同値 setAttribute の抑止 | 改善 |
|---|---|---|---|---|---|
| `baseline` | 190 | 6.7ms | 1.5ms | **1.0ms** | 6.7× |
| `rich` | 301 | 21.4ms | 4.6ms | **2.8ms** | 7.6× |
| `wide` | 2,001 | 53.3ms | 15.0ms | **6.4ms** | 8.3× |
| `mixed` | 5,000 | 134.7ms | 36.6ms | **15.9ms** | 8.5× |

やったことは 2 つ:

1. **要素を使い回す** — ノード id をキーに `<g>` と エッジの `<path>` を保持し、
   位置(transform)と class だけ毎回更新する。内側(rect / label / カード行)は
   「内容シグネチャ」が変わったノードだけ作り直す。
2. **同じ値の setAttribute を書かない** — 直前に書いた transform / class / d を
   覚えておき、変化していなければ DOM に触らない。
   (1) の後はこれがプロファイル上の最大コスト(179ms/窓)だった。

CPU プロファイルの変化(`mixed`、15 打鍵ぶんの self time):

| 関数 | 改修前 | 差分レンダ後 |
|---|---|---|
| `(program)`(ブラウザ内部の style/layout) | 2,020ms | **614ms** |
| `createElementNS` | 107.8ms | **消滅** |
| `append` | 94.9ms | **消滅** |
| `replaceChildren` | 154.5ms | **消滅** |
| `setAttribute` | 197.1ms | 179.5ms → さらに抑止 |

要素の生成・破棄が上位から完全に消えた。

## 注意: 「1文字入力の遅延」の測り方を変えた

改修前のハーネスは「keydown → `#map-svg` の MutationObserver 発火」を測っていた。
**差分レンダリング後はこの測り方が成立しない**: 本文に 1 文字打っても地図の DOM は
変化しないことが多く、サンプルがほとんど取れなくなる(実際 41 → 2 に落ちた)。

そこで **keydown → 次のフレーム** に変えた。必ず発火し、体感遅延と一致する。
**改修前の数値とは定義が違うので直接比較してはいけない。** 比較したいときは
上の「applySnap + render」を見ること。

新しい定義での実測(40 サンプル):

| 文書 | ノード | p50 | p95 | 40 打鍵中に地図が変化した回数 |
|---|---|---|---|---|
| `fat` | 3 | 3.7ms | 16.1ms | 3 |
| `baseline` | 190 | 9.3ms | 16.0ms | 4 |
| `deep` | 200 | 10.2ms | 16.4ms | 3 |
| `rich` | 301 | 9.9ms | 17.1ms | 3 |
| `wide` | 2,001 | 17.5ms | 22.1ms | 3 |
| `mixed` | 5,000 | 44.2ms | 73.9ms | 3 |

最終列が効いている点: **本文への打鍵はもう地図をほとんど触らない**
(40 回中 3〜4 回だけ。改修前は毎回全再構築していた)。

## まだ残っているもの

`mixed` の p50 44.2ms は、DOM 生成ではなく**毎打鍵で走るレイアウト計算と
コンテンツ行の再走査**が主因(`render` 76.5ms、`measure` 46.2ms、
`placeF` 17.1ms、コア境界の `JSON.parse` 30.7ms / 窓あたり)。
