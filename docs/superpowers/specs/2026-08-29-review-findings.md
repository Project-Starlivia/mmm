# I. CommonMark 検証（実測）

## I-1（致命）hidden は不透明な HTML ブロック

HTML block type 2 は `<!--` で開き、**`-->` を含む行でだけ**閉じる。空行では閉じない。
内部ブロックは一切生成されない。実測:

| 入力 | AST |
|---|---|
| C19 元 | `ATXHeading1 r` / `ATXHeading2 a` / `ATXHeading3 b` / `CommentBlock [18,34]` — `### c` は heading ではない |
| C19 新 | `ATXHeading1 r` / `CommentBlock [5,34]` — **a, b, c いずれも AST に存在しない** |
| C20 元 | `ATXHeading1 r` / `CommentBlock [5,26]` |
| C14 元 | `ATXHeading1 r` / `CommentBlock [5,27]` / `ATXHeading2 c` |

帰結:

1. 畳んだノードの id・label・子構造を得るには、生テキストを剥いで**再帰的にサブパース**し
   外側の木へ接ぎ木するしかない。§2 のアーキテクチャにも §4 の Model にも無い層
2. サブパースの span は領域内ローカル座標。文書座標への足し戻し ＝ **手計算オフセット**
   ＝ §1 処方 1 が禁じた当のもの
3. リスト項目内では **1 行目だけコンテナの字下げが剥がれ、2 行目以降は剥がれない**
   （実測: `CommentBlock "<!--\n\n  - b\n\n  -->"`）。デインデント量が行ごとに違う
4. **閉じ忘れが未カタログ** — `-->` が無いと `<!--` 以降 EOF まで 1 ブロック。map が空になる
5. **リスト形ノードを畳むケースが 29 件中 0 件**。実測すると兄弟を包むとリストが 2 本に割れ、
   開き直すと tight/loose が変わる

## I-2（致命）frontmatter は封筒ではない

対になっていない。2 本目の `---` は **setext 見出しの下線**。実測:

```
---\nimage-folder: img\n---\n\n# r\n
→ HorizontalRule [0,3]
   SetextHeading2 [4,25] "image-folder: img\n---"
   ATXHeading1 [27,30] "# r"
```

リポジトリ実在の fixture（`core/head_wbtest.mbt:34`）はさらに悪い:

```
---\n# YAML のコメント\nimage-folder: ./img/\n---\n\n# r\n
→ HorizontalRule
   ATXHeading1 "# YAML のコメント"          ← 幽霊のルート木が 1 本増える
   SetextHeading2 "image-folder: ./img/"
   ATXHeading1 "# r"
```

`head_wbtest.mbt:79` の `tags:\n  - a` を含む fixture は `- a` が枝ノードになる。

旧 core は `core/parser.mbt:98`（先頭の `---` から次の `---` まで）と `core/doc.mbt:60` の
`Head?` でこれを解いていた。新設計はそれを捨てたことに気づいておらず、§8 の旗にも無い
＝ **出荷済み機能 `image-folder` の退行リスクが不可視**。

## I-3（致命）`#######` は CommonMark では段落

ATX の開き列は 1〜6（spec 例 62）。実測で `#######` → `Paragraph`。
C3 備考「読みは 7 個以上も見出しとして受ける」は §2 の「純 CommonMark」と両立しない。
純 CommonMark を採ると、7 個目を打った瞬間に**そのノードが map から消え、子が再親化する**。

## I-4（高）C10 と C24 で「隙間」の定義が食い違う

C10 の定義は「空白と区切り線しか無い**区間**」。C24 は `## a` と `## b` の間に `text` が居るので
この定義に違反し、書き込んだ `---` は flesh → **flipSide が投影に効かない**（法則 2 が静かに破れる）。

成立させるには「骨格行間の区間のうち、空白と区切り線しか無い**末尾部分**」と定義し直す必要がある。
ただし末尾定義だと、ユーザーが `---` の**後ろ**に散文を 1 行足すだけでトグルが消え、
以降の枝の側が全部反転する（新しい爆風）。

## I-5（高）C29 の一様シフトはタブで崩れる

スペースだけなら型不変は成立（実測確認）。しかしタブは +2 スペースで一様に動かない:

```
- a\n\n  \tcode?\n\n- b     → Paragraph （"  "+tab → 桁 4、相対 2）
  - a\n\n    \tcode?（+2）   → CodeBlock （"    "+tab → 桁 8、相対 4）
```

C29 は型不変検査を置くと書くが、**落ちたときの回復手順が無い**。

## I-6（中）C23 の loose 化の因果が逆

loose の条件は「項目が空行で区切られている」または「項目が**空行を挟んで** 2 ブロックを含む」。
ブロック追加そのものではない。実測:

- `- a\n  ```\n  x\n  ```\n- b` → 項目 a に FencedCode が入るが **tight のまま**
- `- a\n  ![](i.png)\n- b` → 空行が無いと遅延継続で段落に吸われ、
  `Paragraph "a\n  ![](i.png)"` ＝ **a のラベルが 2 行に壊れる**

結論は正しいが理由が違う。原因は空行で、しかも空行は副作用ではなく**必須**。
「フェンス content なら tight を保てる」という抜け道と「空行が無いとラベル汚染」という
本当の危険を両方見落としている。

## I-7（中）C10 / C11 の元 map が C22 と矛盾

C22 は「散文は model に登録されない不可視の同居人」と書くのに、C10 の map は
`head["head<br>content01<br>content02"]`、C11 は `a["a<br>body"]` と**素の段落を content として積んでいる**。
実測でも content01 / body はただの `Paragraph`。C29 の `a["a<br>code"]` は Code が Content なので正しい。

## I-8（中）リスト形の枝への区切り挿入が未カタログ

区切りを書く 7 ケース（C4, C8, C9, C17, C18, C24, C26）が全部見出し形。実測:

```
# r\n\n- a\n\n---\n\n- b\n- c\n → BulletList[a] / HorizontalRule / BulletList[b,c]
```

**リストが 2 本に割れる**。リスト同一性・tight/loose・（順序リストなら）番号の連続が壊れる。

## I-9（低）C21 の拒否条件がラベルを含んでいない

`## arrow --> here` のようにラベル側に `-->` があっても同じ行で早閉じする。
`-->` は見出しテキスト内でエスケープできない。拒否条件は **flesh ＋ ラベル**へ。

# II. レッドチーム（N30〜N51）

## S 級 — 憲法か法則 2 が正面から壊れる

### N30: 側の符号化が 1 ビット足りない — flipSide が「別のノード」を飛ばす

```md
# r

## a

## b
```

`flipSide(a)` — 右側の先頭の枝 a を左へ移す。

期待は L, R。put は a|b の隙間に `---` を書くが、再パースすると **a が右・b が左**。
ユーザーは a をつまんだのに **b が飛ぶ**。

枝が N 本なら隙間は N−1 個 → 区切りの配置は 2^(N−1) 通り、側の割り当ては 2^N 通り。
**区切りは側の列を「全体反転を除いて」しか表現できない**。ゆえに「先頭の枝は右」という
暗黙の規約が要り（C4・C17 が前提にしている）、その規約がある限り:

- 「全部左」の文書は**書けない**
- 先頭の枝の flipSide は**表現不能** — put が何を書いても法則 2 が破れる
- 1 本ずつ flip して「全部左」を作ろうとすると、最後に全部右へ跳ね返る

回避は「根の骨格行と最初の枝の間の隙間」にもトグルを認めることだが、
`# タイトル` 直下の飾りの `---` を持つ**ごく普通の md の左右を勝手に反転させる**
（かつ N35 でその `---` を巻き添えに消す）。どちらの角も刺さる。

### N31: 「正規の深さ」と「親の実レベル」の衝突 — indent が無編集・無変化で黙って失敗する

```md
# r

## a

#### b

#### c
```

（C16 の規則により `####` は深さ 3。b, c はともに a の子）

`indent(c)` — c を b の子にする。

c の新しい深さは 4 → C16 に従うと `#### ` → **元と 1 バイトも変わらない**。
再パースしても c は b の兄弟のまま。操作が成功したように見えて何も起きない。

`#` の数は**深さではなく包含関係**を決める。正しくは **親の実レベル + 1** で書くしかないが、
それは C16 と正面から矛盾する。親の実レベルで書く方式に倒すと:

- `###### x` が深さ 2 に居るだけで、その子は深さ 3 なのにリスト形強制
  （C3 の「深さ 6 で打ち止め」は深さではなく**レベル**の規則だったことになる）
- 同じ深さの兄弟が `####` と `###` で混在する文書（合法）で、追加と移動が別々の形を書く

### N32: マーカーの正規化が content indent を動かし、触っていない flesh のブロック型を変える

```md
# r

-   a

      x

- b
```

`-   a` は content indent 4。`      x`（6 スペース）は相対 2 → **段落**。

`rename(a, "a2")` — 骨格行 1 本だけを触る。

正規綴り `- a2`（content indent 2）になると `      x` は相対 4 → **インデントコードブロック**に化ける。
1 文字打っただけで散文が code に変わり、Model の Content も変わる。

「形 ＝ マーカー + 字下げ」の定義が**マーカー後のパディングを形の一部と認めていない**。
content indent は**子孫と flesh の相対字下げの原点**であり、原点を動かすことは
範囲外バイトの意味の書き換え。逆向き（`- a` → `10. a`）も同型。ordered list の正規形も未定義。

### N33: リスト形の枝は見出し形の兄弟より後ろに置けない — 並べ替えで親が変わる

```md
# r

- a

## b
```

（形の混在は**合法かつ普通**）

`move(b, r, 0)` — b を a の前へ。

```md
# r

## b

- a
```

再パースすると `- a` は b の節の中 → **a が b の子になる**。op_model は [b, a] の兄弟。
法則 2 が単純な並べ替えで破れる。逆に `move(a, r, 1)` は**テキスト上に置ける場所が存在しない**。

「形の真似」は**新規ノードの形**しか決めておらず、既存ノードの転形を規定していない。
転形を入れると次が壊れる:

- 見出し形は「**自分の content が子の後ろにある**」状態を表現できない:

  ```md
  - a

    - b

    ![x](x.png)
  ```

  a.contents = [x], a.children = [b]。見出し形へ転形すると画像は b の節に落ち、
  **content の所有者が黙って子へ移る**
- 見出し → リストの転形は flesh の一様字下げを伴う。C11 備考「この原始手術はリスト形でしか
  発火しない」は**事実として誤り**

### N34: 畳んだ枝の側は原理的に表現できない

```md
# r

## a

<!--

## b

-->
```

`flipSide(b)` — 畳んである枝 b を左へ。

a と b の骨格行の間には `<!--` という空行でも区切り線でもない行がある。
隙間の定義を満たさないので、そこに書いた `---` はトグルとして読まれない → **flip が跳ね返る**。

定義から自動的に「畳んだ枝は左右を切り替えられない」が導かれるのに、記述も拒否規則も無い。
C20 の「個別に包み直す」を実行すると隙間が `-->` `<!--` で細切れになり、側の列全体が符号化不能になる。

### N35: 区切り再計算が「根の枝でない隙間」を巻き添えにし、ユーザーの `---` を消す

```md
# r1

## a

---

# r2
```

（C27 が「木と木の間の `---` は保全される」と明言しているのと同じ文書）

`add(a)` — a に子を追加する。

新しい子は a の部分木の末尾＝**この隙間の直前**に挿入される。隙間が「触った」に該当すると
区切り再計算が走り、`# r2` は枝ではないので側を持たない → 「トグル不要」 →
**ユーザーの `---` が削除される**。

もっと悪い同型:

```md
# r

## a

### x

---

### y
```

`add(x)` — x と y は同じ枝の子孫なので側は同一 → 「不要」 →
**節の中の意図的な水平線が消える**。憲法第一条への直接の反例。

「側の列が意味、区切りはその投影」は**根の枝スロット間の隙間にしか適用してはいけない**規則なのに、
隙間の定義は文書中のあらゆる骨格行の間に当てはまる。かつ「触った隙間」の境界が未定義（旗 5）。

### N36: outdent で根に昇格すると、後続の兄弟が全部その根の子になる

```md
# r

## a

## b

## c
```

`outdent(b)` — b を根にする。

その場に `# b` と書くと `## c` は b の節に入る → **c が b の子になる**。
正しくするには長距離移動が要り、「差分 ＝ 書く範囲の狭さ」が崩壊する。

見出し形の深さは**位置と包含が同一の軸**にある。C13（枝への outdent）が成立するのは
根の深さが動かないからにすぎない。`indent(root)` も未定義。

## A 級 — 未定義領域・拒否規則の欠落・爆風半径の新種

### N37: `<!-- -->` の内側は CommonMark の AST に存在しない

I-1 と同一。get は領域内部に対して**第 2 のパーサとオフセット写像**を持たねばならず、
処方 1 の例外を最も壊れやすい場所に開ける。内部の `---` が側のトグルか、
内部の隙間規律は何か、が全部未定義。

### N38: unhide で行頭 `<!--` が生き返り、以降の文書を飲む（C21 の対称ケース）

```md
# r

<!--

## a

<!-- inner note

## b

-->
```

`toggleHidden(a)` — a を開く（C20 に従い領域を解散し b を包み直す）。

```md
# r

## a

<!-- inner note

<!--

## b

-->
```

`<!-- inner note` が HTML ブロックを開いて次の `-->` まで飲む →
**b が Model から消え、包み直したマーカーが無効化される**。C21 の拒否判定は発火しない。

「畳む側の危険 ＝ `-->`」しか見ていない。**開く側の危険 ＝ 行頭 `<!--`** が対称に存在する。
関連: `toggleHidden` は**対合でない**（C19 で吸収された子孫の畳み状態は二度押しても戻らない）。

### N39: 区切りの削除／挿入がリストを併合・分割し、tight/loose と序数を変える

```md
# r

1. a

---

1. b
1. c
```

（描画は「1.」「1. 2.」）

隙間が触られて区切りが不要になると:

```md
# r

1. a

1. b
1. c
```

2 つのリストが **1 つに併合**され描画は「1. 2. 3.」。さらに空行規律が要求した空行で **loose 化**。
b・c のバイトは無傷なのに序数も段落化も変わる。逆向きは 1 つのリストが 3 つに割れ、
「1. 2. 3.」→「1. 1. 1.」。

設計は区切りを「意味を持たない側の投影」と扱っているが、**`---` は CommonMark ではブロック境界**。
既知の爆風（tight→loose）は content 追加に限定されているが、実際には**区切りの有無そのもの**が
範囲外バイトの描画を変える。

### N40: リンク参照定義は文書全域 — 爆風半径に距離の上限が無い

```md
# r

## a

[logo]: img/logo.png

## b

![logo][logo]
```

`toggleHidden(a)` — a を畳む。

`[logo]: ...` がコメントの中に入って参照定義として**死ぬ** → 文書のはるか下、
パッチ範囲外にある b の画像が壊れる。`delete(a)` でも同じ。

「爆風半径は操作対象の骨格 + 近傍の隙間で吸収する」という前提が偽。
参照定義（と GFM の脚注定義）は**文書スコープ**。近傍スナップでは原理的に吸収できない。

### N41: setext ノードの骨格は 2 行 — rename/delete が幽霊の側トグルを残す

```md
# r

a
---

## b

## c
```

`rename(a, "a2")` — put は常に ATX を書く。

骨格行を 1 行だと思って置換すると:

```md
# r

## a2
---

## b

## c
```

`---` は ATX 直後なので**区切り線**になり隙間に落ちる → **b と c が左へ跳ぶ**。

C28 は「触らない限り残る」しか書いておらず、触ったときに骨格が 2 行であることを規定していない。
「骨格行」という単数形の語彙自体がこのケースを隠している。

### N42: ラベルは正規形の綴りで往復できない

`rename(a, "a #")` → put は `## a #` を書く → 閉じ列規則でラベルは **`a`** に戻る。

| ラベル | put が書く | 再パース後 | 症状 |
|---|---|---|---|
| `a #` | `## a #` | `a` | 末尾が消える |
| `  x` | `##   x` | `x` | 前後空白が消える |
| `- x`（リスト形） | `- - x` | 空ラベル + 幽霊の子 | 子が生える |
| `# x`（リスト形） | `- # x` | 空ラベル + 幽霊の子 | 見出しが生える |
| `x\ny` | 2 行 | 別ノード | 骨格が割れる |
| `x -->` | — | — | 祖先の畳みが早閉じ |

さらに **Node.label の定義が未定義**: `## a **b**` のラベルは生テキストか inline レンダ結果か。
レンダ結果なら「同じ文字列で rename」が `## a b` を書いて**ユーザーの強調を破壊**する。

「書く語彙は常に正規形」は**書ける文字列の集合が閉じている**ことを暗黙に仮定しているが、
ATX/リスト項目の綴りは任意文字列を表現できない。エスケープ規則か拒否規則が必須。

### N43: 照合の取り違えは「選択ズレ止まり」ではない

```md
# r

## a

## 
```

`add(r)` の直後にユーザーが 1 文字打つ。

put は編集集合を返すだけで、**生まれたノードの id を返す経路が無い**。
空ラベルの兄弟が 2 つ並んだ時点で位置以外の手掛かりは無く、取り違えると
**打鍵が既存ノードのラベルを書き潰す**。

**選択は次の操作のオペランド**なので、照合の誤りはそのままテキスト破壊に昇格する。
put の戻り値に「作られた/動かされたノードの新しい位置」が無い。

## B 級 — 規則の穴・未定義

### N44: タブ字下げの flesh は「+2 スペース」で動かない

```md
# r

## a

	code

## b
```

（`\tcode` は列 4 → 相対 4 → インデントコードブロック）

先頭に 2 スペースを足すと `  \tcode` → タブは次のタブストップ **列 4** へ進むので**列は 1 も動かない**。
相対字下げは 4 → 2 になり、コードブロックが段落に化ける。

C29 の型不変検査は「壊れたこと」を検出するが、**検出後どうするか**（拒否か、タブ展開か）が無い。
タブ展開は flesh の書き換えなので逐語原則に反する。「タブを含む flesh を持つ部分木は
再インデントを伴う move ができない」＝ **大量の拒否**が規則から導かれるのに、リストに載っていない。

### N45: content の継ぎ目に空行規律が無く、content の認定範囲も未定義

```md
# r

## a

text
```

`addContent(a, image)` — 空行なしで書くと `text\n![](x.png)` → **段落に溶けて inline 画像になる**。

get がブロック画像しか拾わないなら操作は無言で失敗（法則 2 破れ）。inline も拾うなら、
既存の散文 `see ![k](k.png) too` の k が content として map に出て、
`moveContent(k, …)` が**文の途中から画像を切り出す ＝ flesh の書き換え**を要求する。

### N46: 空行規律が内部で矛盾する

```md
# r

- a
- b
```

`flipSide(b)` — 「リストの継ぎ目は兄弟の間隔を真似る」（空行なし）と
「区切りの前に空行 1 本」が同じ 1 箇所で衝突し、優先順位が無い。
空行を入れると N39 の loose 化を必ず引き起こし、入れないと C24 の setext 罠が復活する。

### N47: 領域が部分木と一致しない手書きコメント

```md
# r

## a

<!-- ## draft -->

<!-- markdownlint-disable MD013 -->

## b
```

1 行コメントも HTML ブロック type 2 → 内部を解釈するなら
**`draft` が畳まれたノードとして map に出る**（コメントアウトした行が復活する）。
lint ディレクティブは「枝を 0 本包む領域」で、C20 の解散・包み直しが移動させると
**ディレクティブの適用範囲（パッチ範囲外の行）が変わる**。
a の部分木の途中で始まり b の部分木の途中で終わる領域も書けるが、hidden 旗を誰に立てるかが未定義。

### N48: `#######` は CommonMark では段落

I-3 と同一。「CommonMark 突き合わせテスト」が最初に落とすはずの記述。

### N49: コンテナ接頭辞（blockquote・リスト項目の内側）が未定義

```md
# r

> ## a
>
> ## b
```

`> ## a` を解釈するなら、put は骨格行・区切り・コメントマーカーを **`> ` 付きで**書かねばならない。
列 0 に `---` や `<!--` を書いた瞬間に引用ブロックが終わり、文書構造が崩壊する。
根がリスト項目（`- r1`）のとき、側のトグル `---` を**どの字下げに**書くかで
根のリストを終わらせるか内側リストを終わらせるかが変わる。
設計の「正規形」はコンテナ文脈を一切持っていない。
（解釈しないなら、引用の中だけの文書は map が空になり `add()` の書き込み先が未定義。）

### N50: エンコーディングの罠 — BOM / CRLF / span の単位

- 先頭に BOM: `﻿# r` は**段落**。最初の根が消え `## a` が根に繰り上がり、
  C26 の「先頭の `---` 対は封筒」という位置規則も 1 バイトずれて成立しなくなる
- CRLF 文書: put が書く行末と「空行」の判定が `\n` 前提だと空振りするか混在する
- span の単位: `@lezer/markdown` は UTF-16 オフセット。実装側がバイトなら
  **日本語の文書は全部ずれる**。絵文字（サロゲートペア）でコードポイント単位の算術も割れる

「境界を渡るのは値だけ」と決めた一方で、**その値の単位を決めていない**。
日本語文書が主対象である以上、最初に固定すべき定義。

### N51: 同位置への move で骨格行が勝手に整形される（法則 1 の穴）

```md
# r

## a

#### b
```

`move(b, a, 0)` — b を（既に居る）a の先頭の子へドロップする。

木としては無変化だが「触った骨格行は正規綴り」に従うと `#### b` → `### b` が書かれる。
**操作していないのに md が整形される**。法則 1 の「無操作」がユーザー操作の非存在を指すのか
木の変化の非存在を指すのかが決まっていないため、
UI で最も起きやすいドロップ（元の位置に落とす）が憲法違反になる。

## レッドチームの総括

最も重い 3 つは **N30（側が 1 ビット足りない）**、**N31（正規の深さと親の実レベルの衝突）**、
**N32（マーカー正規化が content indent を動かす）**。いずれも「正規形で書き直す」という
put の中核方針が、md の**位置依存な意味**（包含・原点・符号化容量）と衝突して起きており、
個別のケース追加では塞げない。

N33・N36 は「木の語彙で言えるが md に書ける場所が存在しない操作」の実在証明で、
**転形規則と拒否リストが設計に丸ごと欠けている**ことを示す。
N35 は憲法第一条への直接の反例であり、しかも設計自身の C27 と矛盾する。

C10・C24・C25・C26・C28 のような**読みの罠**への守りは筋が良く、
破れているのは**書き**の側（正規形・隙間・転形・拒否）に集中している。

# III. アーキテクチャ批評（S1〜S12）

## 先に固定された「正しい部分」

- **パースは律速ではない（実測済み）**。`docs/audit/PERF.md` §6: 5,000 ノード / 191KB の

- **「区切りは有るか無いか」は最良の判断**。これ 1 つで `core/seps.mbt:477-611`（`sweep_seps`、
  xor 畳み込み 135 行）と `sep_marks`/`map_offsets` の目印機構が丸ごと消える。病理 3 と 4 が同時に死ぬ
- **put をバイトの唯一の書き手にすると既存の重複が実際に消える**（S6 参照）

## S1（致命）「本物の CommonMark AST」は存在せず、自分の仕様と矛盾する

- `core/moon.mod` に外部依存ゼロ。MoonBit に CommonMark パーサは無く自作しかない
  （spec は 650 超の例）
- `core/parser.mbt:1-3` が明示的に書いている: 「深さに上限を置かないので既成の Markdown パーサは
  使えないが、必要なのは行のオフセットとフェンス / hide 領域の追跡だけなので、これで足りる」。
  旧設計は**意識して選んだ**。処方 1 はその撤回だが、撤回の理由が §1 に無い
- 矛盾: C3 の `#######`（I-3）/ `core/parser.mbt:558-566` が意図的に `- - -` を
  thematic break として読まないと決めている / `core/parser.mbt:285` が `#` の後に空白を要求するので
  `##` 単独を見出しにしない（CommonMark は受ける）/ `> ## a` を読むか

**決めること**: 「純 CommonMark」を降ろし**「ブロック構造だけ CommonMark 準拠」**に絞る。
パーサ差し替えを最初にやらない。`@lezer/markdown` を**ゲートではなく計測ハーネス**として先に走らせ、
`test/_helpers.ts:corpus()` と `randomDoc()` に対して「現スキャナと lezer のブロック木が
何件・どの規則で食い違うか」を数える。§8 旗 3 を旗から**前提**へ格上げする。

## S2（致命）照合は「被害は選択ズレ止まり」ではない。id は破壊的操作の宛先である

- `src/main.ts:520` — `core.deleteNodes([...selection])`。照合が別ノードへ id を貼れば別の部分木が消える
- `src/mindmap.ts:1234-1242` — ドラッグ中の id 集合が離した瞬間に宛先になる
- `src/mindmap.ts:413-416` に**この正確な危険への既存の守り**がある:
  「掴んでいたノードが消えていたらドラッグごと畳む（消えた id を指したままドロップすると、
  無関係なノードが動く）」。この見張りは `boxes.has(id)` で id の消滅を見るので、
  **照合を入れた瞬間に構造的に効かなくなる**
- **分割と併合**: 見出し行の途中に改行を打つと 1 ノードが 2 つになる。ラベル一致で照合するなら
  **同名兄弟で必ず取り違える**。しかも空ラベルのノードは put 自身が量産する（C1/C2/C5）
- **旧 core の id 保存は決定的だった**。`core/edit.mbt:55-113` の `map_offsets` で位置を写し、
  `rebuild_nodes(id_at)` が `id_at.get(h.from)` で厳密一致させる。
  設計は**決定的だった仕組みをヒューリスティックに格下げしている**。
  処方 3 が「手計算オフセットを再構築をまたいで持つ」（悪）と
  「権威ある編集集合を通して写す」（正確）を混同したのが原因

**決め方**: **照合を捨てる**。同一性は (1) 骨格行の先頭オフセットを**その編集の ChangeSet で写した位置**
（CodeMirror の `ChangeDesc.mapPos`）、(2) 移動のようにオフセットが死ぬ操作は
**put が `(旧→新)` の対応表を編集集合と一緒に返す**（`core/move.mbt:172-190` の `rels` が
既に内部で計算している）、(3) 骨格行が本当に消えたら id は死ぬ（`mindmap.ts:413` の弁が生き続ける）。
これで**推測地点はゼロ**になり、旗 4 が課題ごと消える。
加えて async を跨ぐ経路（`main.ts:888` 画像保存 / `:418` クリップボード / `:403` お絵描き）は
`id` 単体ではなく `{rev, id}` を持つ。

## S3（高）法則 3 は自明か偽。法則 1 は空。検査になっていない

- **法則 3**: 編集集合は `{from:0, to:len}` でも書ける。「パッチ範囲 ＝ 編集集合が触った範囲」なら
  トートロジー、それ以外なら「構造上自動」は偽。実際 **C11/C29 は部分木の flesh 全行を書き換える**
- **法則 1**: op が無いなら put は呼ばれない。§7 は `put(get(s),s)=s` と同型と書くが、
  BX の put は**状態**を書き戻す関数でこの設計の put は**操作**を受ける関数なので同型ではない

**直し方**:
- **法則 3′（範囲予算）**: 編集集合が触る行集合 ⊆ {op が名指しした骨格行} ∪ {その部分木の骨格行}
  ∪ {隣接する純粋な隙間の行}。flesh 一様シフトは**名前付きの例外**としてリストに載せる
- **法則 1′（不動点）**: 意味的に恒等な op で編集集合が空（N51 がまさにこれ）。
  旧 core は実際に踏んでいる — `core/history.mbt:128-134` に
  「打ち消し合う 2 本で undo が空振りし、しかも redo が捨てられていた」と記録がある
- **法則 4（追加）**: get が骨格として拾う行の集合が `@lezer/markdown` のブロック木と一致する。
  §0 の自己定義を検査する法則が現状 1 つも無い

## S4（高）法則 2 の判定可能性 — 「崩れた文書」の定義が循環している

「正規形の文書で全域成立」と書くが**正規形の定義がどこにも無い**。
「破れたら崩れていたことにする」という反証不可能な命題になる。

一方で**難所ではないところ**:

- Model の等価関係は**既にある**: `test/_helpers.ts:79-88` の `shape()` が
  親を id ではなく文書順の添字で表す。side/hidden/contents を足せばそのまま使える
- 生成器も**既にある**: `randomDoc(seed)`（`_helpers.ts:120-155`）が
  フェンス・区切り・HTML コメント・深さ飛び・空ラベル・CRLF・複数ルートを狙って生成する。
  `corpus()` は実 .md 全件

**直し方**: `canonical(md): Bool` を独立した小さい述語として先に書き、
**canonical な種から put で到達した文書は canonical という閉包性（法則 5）自体をファズで検査**する。
また **op_model の見積もりを直す** — §5 の「数行」は木だけの話で、
実際は side・hidden 吸収・h6 打ち止め・拒否規則を含めて数百行。
見積もりが外れると製品コードから借りたくなり、**§5 が禁じている裏口が開く**。

## S5（高）Model にスパンが無いと UI が成立しない

## S6（中〜高）put / CodeMirror の境界 — 旗 1 は二択ではない

**憲法はすでに破れている**: `src/edits.ts:72-78` の `insertBlock` は
`core/heading.mbt:115-131` の `block_insert` と**同じ規則の 2 つ目の実装**であり、
**既に食い違っている**（mbt は `preceded_by_blank` が空白だけの行を跨いで見る、
ts は `at >= 2 && text[at-2] !== "\n"` だけ。`"# a\n \n"` で挙動が割れる）。
新設計は C22/C23 でここを実際に殺す（`src/edits.ts` 79 行が消える）。

**mbt が持ち続ける理由が無いもの**: `core/edit.mbt` 全 113 行、`core/history.mbt` 190 行、
`src/main.ts:314-377` の tag 機械 60 行。CodeMirror の `ChangeSet.compose/map/invert` と
`history({newGroupDelay})` が同じことを IME と複数カーソルまで含めて正しく持っている。
しかも `src/editor.ts:104` は現在 **history 拡張を入れていない**。
§6 が「undo の通貨はテキスト差分」と宣言している ＝ CM の history そのもの。

**決め方**: 決めるべきは「put を誰が実装するか」ではなく
**「バッファ・履歴・選択・位置写像を誰が所有するか」**。答えは CodeMirror。
put は「木の語彙の op → `(span, 置換文字列)` の列 + id 対応表」を返す**純関数**として mbt に置く。
TS はそれを 1 つの CM トランザクションに詰めるだけ ＝ **TS は 1 バイトも「選ばない」**ので憲法は守られる。

副産物: `core/relevel.mbt:28-62` の st 保存/復元ハック（「rebuild_nodes が st の欄を増やしたら
ここにも同じ欄を足すこと（st.head を一度足し忘れた）」という自白付き）が消える /
`test/_helpers.ts:7` の「MoonBit コアはモジュールグローバルな状態を 1 つ持つ」という縛りが消える /
`getText()` の持ち主が CM 1 つになる。

## S7（中〜高）全再パースのコストは「パース」ではなく「二重パース」と「境界」にある

- パース自体は安い（実測済み）
- しかし §2 の図は **1 操作あたり 2 回パースする**と読める（put が骨格行のオフセットを知るために
  パースし、その後 get がもう一度）。5,000 ノードで +19ms
- 境界コスト: `PERF.md` §3-2 が `JSON.parse` を **28.4ms / 窓（15 打鍵）** と実測。
  新 Model は入れ子の木 + contents 配列なので確実に大きく、照合は旧新**両方**を要求する
- **設計書に無い事実**: CodeMirror は同じ文書を `@lezer/markdown` で
  **すでに毎トランザクション増分パースしている**（`src/editor.ts:101`）。
  つまり今すでに二重パースしており、parse を TS 側に置けば 1 回になる

**直し方**: put の型を `put(md, op)` ではなく **`put(get の結果, op) -> edits`** にする /
境界の JSON を捨てるか Model を平坦形にする / 「N ノードで get + 照合 + 境界が X ms」の予算を先に書く。

## S8（中）レース — 今は無いが、設計が非同期を招き入れている

現状は完全同期（`src/main.ts:368-373`）でレースは無い。既にある async の穴は
`:888`/`:418`/`:403` で、今は id で守っている（S2 が壊すのはここ）。

**オフセットの単位が仕様に無い**。CodeMirror は UTF-16。現 core も `s[i]` が UTF-16 単位で、
`test/roundtrip.test.ts` に「絵文字とサロゲートペア」のケースがある。
新しい parse 層がバイトオフセットを採ると非 BMP 文字で全オフセットがずれる。
`src/main.ts:675-681` に同種の事故の記録: 「CodeMirror が出す LF 基準のオフセットがコア側でずれ、
打鍵が見当違いの位置に書き込まれて表示と保存内容が乖離する」。

**決めること**: 「put は同期。これは仕様」と書く / オフセットは UTF-16 コード単位と明記 /
put の入力に rev を含め、当てる直前に不一致なら捨てて再計算（`applySnap` の `docGen` ガードと同じ形）。

## S10（中）空ラベル骨格行の「末尾空白」規約は不要

理由に挙げた「空白が無いと `##a` になる」は**現スキャナ（`core/parser.mbt:285`）の制約**であって
CommonMark の制約ではない。CommonMark は `##` 単独を空の ATX 見出しとして受ける。
`-` 単独は現スキャナでも既にリスト項目（`core/parser.mbt:307-308`）。
そもそもラベル入力は map 側の入力欄でやる（`src/mindmap.ts:785-798` の `beginEdit`）。
外の道具（prettier / markdownlint --fix / trim-on-save）が確実に落とす綴りを規約にするのは
「md の自由の上に住む」と噛み合わない。

## S11（低〜中）C22 の挿入点規約は不可視の散文の帰属を静かに変える

示した例では正しいが、**c01 自身を動かすと** body は前のノードの本文の頭に取り残される。
仕様としては §0 と整合しているが、カタログが「動かない」とだけ書いているので読者は逆の期待を持つ。

## 総評と最初に作るもの

憲法（テキストが真実 / put が唯一の書き手 / 毎回全再パース / 区切りは有無だけ / side は Model の属性）は
健全で、旧 core の病理 2・3・4 を**実際に**殺す。とくに「側の列が意味、区切りはその投影」は
`core/seps.mbt` の 135 行を丸ごと不要にする、この設計で最も価値のある 1 手。
法則 2 + op_model は PR #14 のバグの本丸（区切り算術）を正面から撃つ正しい道具立てで、
材料（`randomDoc` / `shape` / `corpus`）は既にリポジトリにある。

一方で **処方 1（本物の CommonMark AST）と照合の 2 点は、いまのままだと病理を殺さず移動させる**。

**着手前に決めること**: (1) 照合を捨てる、(2) 「純 CommonMark」を降ろし解釈範囲の表を先に書く、
(3) バッファ・履歴・選択・位置写像を CodeMirror に渡す。

**最初に作るもの（最短の反証、1 週間規模）**: 既存スキャナを `parse` として据え置いたまま、
get（span 付き）/ op_model と put を **move・flipSide・delete の 3 つだけ** /
`canonical` 述語 / 法則 2・3′・5 のファズ（`randomDoc` + `shape()` の上に載せる）。

**なぜこの 3 op か**: PR #14 のバグの本丸は区切り算術で、それを踏むのは
flipSide（C17）・delete（C8）・move（C13/C18）の 3 つ。

**何が設計を殺すか**: C8/C13/C17/C18 を満たすために put 側の場合分けが増え続けたら殺す。
「1 規則で決まる」という主張が偽だったということ。

**最初に作ってはいけないもの**: CommonMark パーサ、照合、Tidy コマンド、糖衣分類表、UI の削除作業。
