# 木の書き方を 2 つにする（見出しとリスト）

## なぜ

同じ木を `#` でも `-` でも書けるようにする。マップは**どちらでも同じに見える**。

`####` が並んだ `.md` は GitHub で見ると見出しの壁だが、入れ子の箇条書きなら
構造がそのまま読める。テキストが唯一の真実である以上、その真実が mmm の外でも
読めるかは大きい。

```
# root                    - root

## branch A          ⇄      - branch A
[記事](https://…)             [記事](https://…)

### leaf                      - leaf
```

## モード = 「深さ b 以上をリストで書く」の b、ただ 1 つ

3 モードは別々の仕組みではなく、b の値が違うだけ。

| ボタン | b | 書かれ方 |
|---|---|---|
| Head | ∞ | 全部 `#`。深さ 7 は `#######` — **md の制約を超えて積む**（外のツールではただの文字に見えるが、それは承知の上） |
| Hybrid | 1〜6 | 深さ b 未満は `#`、b 以上は `-`（b=1 は List と同じになるが、重なりは無害） |
| List | 1 | 全部 `-` |

## 読む規則 — モードを知らない

パーサは**常に両方を構造として読む**。モードは読みに一切関与しない。

```
^#+(\s|行末)            → 見出し。深さ = # の本数（上限なし）
^\s*[-*+](\s|行末)      → リスト項目。深さ = 直近の見出しの深さ + 1 + 入れ子段数
それ以外                → 直近の構造行の中身（カードになるものはカードに）
```

- **見出しはリストの入れ子をリセットする**。見出しの下のリストは、その見出しの
  子から数え直す。だから混ざった文書も同じ式で読める
- 入れ子の段数は**字下げのスタック**で数える。前の項目より深ければ子、浅ければ
  戻る。2 スペース決め打ちにしない — 他所の 4 スペースもタブも読める
  （タブは 2 桁として比べる）
- フェンス・hide 領域の中の行は、今までどおり構造にならない
- 数字付き（`1.`）は今回は見ない。`-` `*` `+` の 3 つだけ
- 「本文」という概念は持たない。`- x` は必ずノード。**mmm は散文を編集する
  道具ではない**ので、「箇条書きは飾り」という区別が要らない

**不変条件: モードを切り替えてもマップは 1 ピクセルも変わらない。**
（切り替えは純粋なテキストの書き直しで、parse(変換後) ≡ parse(変換前)）

## 書く規則 — b が決める

マップからの追加・編集（add / rename / indent / outdent / move / relevel）が
生む行は、その行の深さ d と b で形が決まる。

- d < b → `#`×d + ` ` + ラベル
- d ≥ b → 2×入れ子 スペース + `- ` + ラベル
  （入れ子 = d − 直近の見出し祖先の深さ − 1。見出し祖先が無ければ 0）

深さの変更は「`#` を 1 本足す / 消す」方式をやめ、**行の接頭辞（`#…` または
字下げ+`-`）をまるごと書き直す** 1 本の機構に統一する。形の境界をまたぐ
移動（見出し→リスト）も同じ機構で済む。

書くときの字下げは常に 2 スペース、印は `-`。

## モードの 3 つの仕事

1. **切り替え** = 文書ぜんぶを b の正規形へ書き直す。1 回の undo で戻る
2. **整形** = いまのモードのボタンをもう一度押すと、構造そのままで正規形に
   揃える（同じ処理の再利用）。見出しブロックは空行で区切り、リストの兄弟は
   詰め、印は `-`、字下げは 2、添付の中身は項目の字下げに揃える
3. **追加の書き方** = 上の「書く規則」

## 自動判定 — 開いたときだけ

```
b = 文書中でリスト項目が現れた最も浅い深さ。リストが無ければ ∞
```

- `init_doc` のときだけ走る。**テキストは 1 文字も書き換えない**
  （整形はボタンを押したときだけ）
- **実行中は不変**。md をどう手打ちしてもモードは動かない。混ざった文書も
  読みは正しく、揃えたくなったらボタンを押す
- モードはどこにも保存しない。テキストが真実で、次に開けば再検知される
- 新規・空文書は ∞（Head）

## UI

md ペイン右上に 3 ボタン `[H] [n+] [L]`。現在のモードが点灯。
Hybrid のボタンには b が出ていて（`3+`）、押すたび 1→2→…→6→1 と巡る。
初期値は検知結果（範囲外なら 2）。

## 置き場所

b は core が持つ（書くコマンドが core にいるので）。
`set_list_from(b)` / `reformat()`、検知結果は `init_doc` の snapshot に載せる。
パーサは各ノードの形（head / list）も覚える — 書く側が接頭辞の範囲を知るため。

## 影響

- 読み込みはテキストを書き換えないので、roundtrip / corpus のテストは
  ノード数が変わっても通る
- 箇条書きを含む既存の `.md` は、開くとノードが増える（この repo の README は
  20 → 45）。想定される使い方ではない、という立場
- 貼り付けの判断（`has_headings`）がリストを構造と数えるかは**今回は触らない**
  （見出しのみ。リスト断片の貼り付け対応は後続）

## 実装で確定したこと（2026-08-25）

- 接頭辞の書き直し（`prefix_edit`）が唯一の深さ変更機構になった。
  indent / outdent / add_parent / move_block / relevel / rename すべてが通る
- rename も接頭辞を正規形に揃える — どの形で書くかはモードに一任
- 貼り付けの relevel は断片を**いまのモードの形**に書き直す。リスト断片も
  `has_headings` が構造と数えるので、貼れば子ツリーになる
- **整形は接頭辞だけでは足りなかった**（`core/format.mbt`）。リストの形では、
  中身の行を項目の中身の列まで字下げしないと、外の Markdown パーサはそこで
  リストを閉じ、続く項目は別のリスト・深い字下げはコードブロックに化ける。
  実際に `@lezer/markdown`（CommonMark）に読ませて確かめた
- 空行の規則は「**どちらかが中身なら 1 つ、構造どうしなら 0**」（リストの形）。
  見出しの形は今までどおり常に 1 つ。ラベルと中身の間に空行が無いと、
  中身がラベルの段落に融合する
- フェンスの中はコード。字下げは塊ごと動かし、空行には触らない
- **フェンスの字下げは囲う項目の中身の列から数える**（`fence_open` の `base`）。
  0 固定だったころ、リストの中のフェンスが認識されず中の `- x` がノードに化けた

## 段取り

1. **読む** — `scan_doc` がリストを構造として拾う。`#{1,}` の上限も外す
2. **書く** — 接頭辞書き直しの機構と、b に従う各コマンド
3. **変換・整形・ボタン** — `reformat()` と md ペイン右上の 3 ボタン

**1 と 2 は 1 つの単位**。読みだけ入れると、リスト文書に `###` が混ざった瞬間、
その見出しがリストの入れ子をリセットして後続の深さが 1 つずれ、木が壊れる。
