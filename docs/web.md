# Web へ戻す

## なぜ

**ブラウザのタブで開くほうが気楽だから。** それだけ。

Tauri が与えてくれたもの（パスの所有・外部監視・文字コードの往復）は、
気楽さと引き換えに手放す。手放せないもの（隣の画像を相対パスで読み書きする）
だけを、ブラウザの手段で作り直す。

## 何になるか

**いまと同じもの。足回りだけが変わる。**

Markdown ⇄ マインドマップの双方向エディタで、2 枚のペインが互いを映す。
`.md` はディスク上の実体であり続ける。変わるのは、その実体に触る手が
Rust からブラウザの File System Access API になることだけ。

そのうえで、**同じことをする道が 2 本ある箇所を畳む。** 削る基準は
「`.md` の見出し構造を空間で編集する」から説明できるかどうか。ただし
**操作の快適さはコアバリューに含む** — 画像がドロップですぐ出ること、
リンクやコードがカードとして見えることは、「あれば良い」ではなく、
この道具が道具である理由そのもの。

## 決めたこと

### 1. ファイルは 1 つずつ開く。フォルダは画像を初めて置くときだけ選ぶ

File System Access API を使う。**Chromium 系でしか動かない**と言い切る。
フォールバック（ダウンロードでの保存）は持たない — 2 本目の道を作れば
そちらでは画像が死に、「実体はただの .md」も壊れる。動く道が 1 本だけ
あるほうが良い。

- **開く** = `showOpenFilePicker()`、または `.md` のドロップ
- **保存** = 開いたハンドルへ上書き。まだディスクに無ければ、本文から導いた
  名前を初期値にして保存先を聞く
- **別名で保存** = 保存先を聞く。元のファイルはそのまま
- **新規** = 空の文書。保存するまでディスクには無い

ファイルのハンドルからは親フォルダに辿れないので、**隣の画像を読み書きする
にはフォルダの許可が要る**。それを求めるのは**画像を初めて置くとき**だけ。
フォルダを開かせてから md を選ばせる形は採らない — 画像を使わない文書に
フォルダの話をさせない。

### 2. 画像は「フォルダを 1 つ選ぶ → 名前を書く」— アプリは確かめない

**フォルダを選ぶとき（初回だけ）**

1. `showDirectoryPicker({ startIn: fileHandle })` でフォルダを 1 つ選ぶ。
   **どこでもよい。** md を含むかどうかをアプリは調べない（`resolve()` で
   調べられるが、調べない — 探査も関与もしないほうが単純）
2. **保存パス**を聞く（初期値 `./`）。これは「**md から見て、選んだフォルダが
   どこにあるか**」の宣言で、フォルダと一対のもの。だから**フォルダを
   選び直すときにしか聞かない**

**画像を置くたび**

3. **名前**を書く（初期値 `yyyy-mm-dd-HHmmss`、拡張子 `.webp` は固定表示）。
   ただの名前ではなく slug で、`assets/shot` のように `/` を入れれば
   選んだフォルダの下にサブフォルダを作る
4. WebP に変換して**選んだフォルダの中に `名前.webp` を書き**、本文に
   **`![](保存パス + 名前.webp)` を挿入する**

md と同じフォルダを選んで `./` のままなら、何も考えなくて合う（ダイアログは
md のあるフォルダで開くので、そのまま「選択」を押すだけ）。`../pics/` に
貯めたいなら `pics` を選んで保存パスに `../pics/` と書く。

読むときも同じ宣言を使う: 本文の `![](p)` が保存パスで始まれば、その残りを
選んだフォルダの中に探す。始まらなければ点線のプレースホルダにファイル名で
出す。**プレースホルダをクリックするとフォルダを選ぶ**（まだ選んでいない
ときの入り口がこれ）。

宣言が実際の配置と食い違っていても、アプリは気づかない — アプリの中では
辻褄が合って見え、ディスク上の md だけが嘘になる。**これはユーザーの責任。**

画像ファイルのドロップは、どこから来たものでも 3 と 4 で選んだフォルダへ
複製する。`.md` のドロップはその md を開く。

### 3. カードは 4 種のまま残す

リンク / 画像 / SVG / コード。「見て分かる」ことがマップの価値なので、
プレビュー 1 種に畳まない。ここは削らない。

### 4. 文字コードと改行は UTF-8 / LF だけ

Shift-JIS の往復も CRLF の往復も、ネイティブだから背負えた要求。
ブラウザでは UTF-8 で読み、UTF-8 で書く。読み込み時に CRLF は LF へ
正規化し、**保存も LF で書く**（元の改行へ戻さない）。

### 5. 外部変更は追わない

`notify` に相当するものがブラウザに無い。ポーリングは持たない
（「見張っているようで見張れていない」のが一番悪い）。他所で書き換えたら、
**開き直せば最新になる**。それだけを約束する。

### 6. 覚えるのはハンドルと、色の好みだけ

IndexedDB にファイルとフォルダのハンドルと保存パス。起動時は前回のファイルを
開き直す（許可の再確認が要るときは、ファイル名欄のクリックで開く）。
localStorage はテーマだけになる。

保存は明示（`Mod+S`）のまま。未保存でタブを閉じようとしたら
`beforeunload` で止める。

## 段取り

各フェーズの終わりに `pnpm test` / `pnpm run test:core` / `pnpm run check`
を通し、コミットする。

git は 2026-08-22 に入れた（それまでは未管理）。最初のコミットが Tauri 版の
現状。作業は `refactor/web` ブランチを `.worktrees/refactor/web` で進め、
終わったら main へ squash merge してブランチと worktree を捨てる。
**main は merge の瞬間まで Tauri 版のまま動く。**

**`core/` と `src/map/` の話で、Web 化とは独立。** Tauri 版のまま進めれば
`pnpm run app` で目で確かめられるので、足回りを壊す前にここを済ませる。

付いてくる。front matter は最初の見出しより前にあるので、いままで通り
どのノードにも属さない。

### Phase 3 — 道を 1 本にする

同じことをする道が 2 本ある箇所を畳む。急がない。

- **リンク / コードのポップアップ**（`Shift+L` / `Shift+C`）を削る。
  MD ペインで打てば済む。URL をノードにペーストすればリンク行になるのも
  そのまま
- **お絵描きポップアップ**（`Shift+D`）を削る。描く道具は他にある
  （戻せる継ぎ目は残す、下記）
- **vim キー**を全部削る（`hjkl` `gg` `G` `zz` `dd` `yy` `p` `u` `s` `cc`
  `i` `a` `A` `I` `o` `O`）。矢印 / `Enter` / `Tab` / `Mod+X/C/V/Z` に一本化
- **パン**: `Space+ドラッグ` だけにする（空白ドラッグ = 矩形選択）。
  中クリックを削る
- **ペインの開閉**: MD / マップ ボタン（マウス）と `Mod+/`（キーボード）は
  同じ操作の 2 つの入口なので残す。**スプリッタのダブルクリック**だけが
  3 本目の別の道なので削る
- **書き出し**: SVG のダウンロードだけにする。WebP とクリップボードコピー
  2 種を削る（4 ボタン → 1 ボタン）
- **ブランドカラー変更**（ロゴのクリック）と favicon の動的生成を削る。
  色は固定。テーマ切替は残す — 暗い部屋で目が痛いのは実用の問題で、
  ブランドカラーは趣味の問題
- ツールバーは **11 ボタン → 8 ボタン**（新規 / 開く / 保存 / ↩ ↪ /
  SVG / MD・マップ / ◑）

## 消えないもの

`core/`（MoonBit）は**一行も変わらない**。テキストが唯一の真実で、構造操作が
文字オフセットの編集セットに落ちるという設計は、ネイティブでもブラウザでも
同じように正しい。`src/editor.ts`（CodeMirror 6）も `src/app/panes.ts` も
`src/map/` の純粋層も、`name.ts` も `paste.ts` も `relevel.ts` も残る。

**消えるのは `src-tauri/` と `src/app/io.ts` の中身だけ。**

## いったん外すが、戻れる継ぎ目を残すもの

**お絵描き**（canvas に描いて WebP で保存）。リンクやコードは md を打てば
済むが、絵は打てない。`Blob` を渡せば置き場所を聞いて `![]()` を挿入する
入り口（`assets.saveToDisk`）はそのまま残るので、戻すときはそこへ繋ぐだけ。

## 未決

### `---` を消したあと、マップはどんな形か

左右の振り分けを**テキストから**消すのは決まった。残るのは、**マップの
見た目まで片側にするか**どうか。core の削減は下の 2 つで同じで、
違うのは `src/map/layout.ts` と `geometry.ts` だけ。

**A. 片側だけ** — ルートは左端に立ち、すべて右へ伸びる。`F_LEFT` も
`placeSide` も消え、`Frame` による射影そのものが要らなくなる（`geometry.ts`
がさらに縮む）。いちばん単純。ただしマップは**横に倒したアウトライン**になる。

**B. アプリが左右へ振り分ける** — テキストには何も書かず、ルート直下の
子を子孫の数で均衡させて左右に置く。`layout.ts` に振り分けの規則が 1 つ
増えるだけ（`F_LEFT` と `placeSide` は残る）。**テキストからは `---` が
完全に消えたまま、根が中心にあって両側へ広がる形は残る。**
代わりに、どちらの側に置くかをユーザーは選べない。

**推し: B。** 「`---` を消す」の本体は、記法・偶数本規則・
`add_side_end` / `move_side_end`・`group` という**テキスト側の仕掛け**で、
それは A でも B でも全部消える。マップが両側へ広がるのは、この道具が
アウトライナではなくマインドマップである理由そのもので、それを守る値段が
純粋関数 1 つの中の 15 行なら安い。
